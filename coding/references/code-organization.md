# 代码组织判定规则

涉及新建文件、提取公共代码、发现重复实现时，用本文件的规则判定。

## 1. 新建文件判定

按顺序问三个问题，任何一步得到肯定答案就停止：

1. **有职责匹配的既有文件吗？** → 放进去。
2. **放入最接近的既有文件，会破坏它的职责边界吗？** 判据：放入后，该文件的一句话职责描述是否需要加"和"才能说清（"解析配置**和**发送通知"）。不需要加"和" → 放进去。
3. 前两步都走不通 → 新建文件，并报备理由（理由 = 说明第 1、2 步为何不成立），新文件必须有一句话能说清的单一职责。

**反模式清单（禁止）：**

- 反射式拆分：每写一个类/函数就开一个新文件（除非项目惯例如此）
- 按技术动作碎片化：`helpers.py`、`utils2.py`、`misc.py`、`tools.py` 式的垃圾抽屉
- 为单个小功能开新目录
- 文件命名带版本/状态后缀：`_v2`、`_new`、`_old`、`_final`、`_improved`、`_backup`，这是硬红线"禁止平行实现"的文件系统表现形式

**关于文件大小**：行数不是拆分依据。拆分的唯一信号是"这个文件里的代码有两个不同的变化原因"（一部分随业务规则变，一部分随存储方式变，就该拆）。

## 2. 公共代码准入测试（common / utils / shared）

把代码放进公共目录前，三个测试必须全部通过：

1. **领域无关性测试**：把这段代码原样复制到一个完全不同的项目，它还成立吗？
   它解决的是"技术问题"（重试、解析、格式化）还是"业务问题"（折扣、审批、配额）？
2. **语义唯一性测试**：各调用方需要的是同一份"知识"吗？如果未来一个调用方要求
   改行为，其它调用方也理应跟着变，才是真正的公共代码；若各方会朝不同方向演化，
   现在的相似只是巧合，不要合并。
3. **接口稳定性测试**：不需要为了伺候不同调用方而添加 flag 参数。如果提取后的
   函数需要 `mode=`、`is_special=` 之类的开关才能工作，说明它不是一份逻辑。

**关键认知：被 import 的次数衡量的是流行度，不是通用性。**

- 反例：`calculate_order_discount()` 被 5 个模块 import → 它属于订单领域，放在 `order/` 模块里，让其它模块 import 订单模块。放进 common 只会让业务规则散落到无人认领的地方。
- 正例：`retry_with_backoff()`、`slugify()`、`parse_iso8601()` → 领域无关，任何项目都能用，进 common。

**依赖方向规则**：依赖只允许指向 common（领域模块 → common），common 永远不依赖领域模块。common 里出现领域词汇，或 common import 了业务模块，都是立即需要报告的违规信号。

## 3. 重复实现的处理

**发现时**（两份实现同一逻辑）：

1. 停止修改。
2. 报告：两份实现的位置、可见差异、哪些调用方分别使用哪份。
3. 询问权威版本，等待确认。
4. 确认后：改动只发生在权威版本上；废弃版本按指示删除或标记 deprecated，不留第三种状态。

**预防**（写新函数前的强制搜索）：

- 搜索函数名的同义词族：fetch/get/load/retrieve/query、check/validate/verify/ensure、convert/transform/parse/format
- 翻公共目录和邻近领域模块的导出清单

**典型症状——修改无效**：改了代码但行为毫无变化，最常见原因就是存在双实现而你改了不被执行的那份。处置方法：在你修改的位置故意抛错或打独特标记的日志，跑一次复现路径。炸不出来 = 改错了地方，立刻去找真正被执行的实现。

## 4. 抽象时机（Rule of Three）

- 第一次写：直接写。
- 第二次重复：容忍复制，加个注释标记重复点即可。
- 第三次出现：抽象的时机到了——但抽象出的代码放哪，仍要过第 2 节的准入测试（多数情况下它属于某个领域模块，而不是 common）。
- 例外：如果三份重复注定同步变化（如协议常量、校验规则），可以提前抽象，
  说明理由即可。
