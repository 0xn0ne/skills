# Coding — 编码工作流的自律框架

> 让 AI agent 写出的每一行改动都**精准、可验证、不制造结构混乱**。它不是风格指南，而是一套「边界 + 心法 + 工作循环」：边界之内给足技术自主权，触碰边界就停下来沟通。
>
> 核心四句话：**先理解后实施 · 单一事实源 · 复用有门槛 · 外科手术式修改**。

## 这是什么 / 给谁用

**不是**代码风格指南、语言规范、框架教程、lint 规则集——它不规定你用 tabs 还是空格。**而是**给编码 agent 的行为约束层：**动手前的侦察义务**（找现有实现 / 找唯一事实源 / 找周围惯例）、**动手时的克制边界**（只改该改的、不建平行实现、不顺手重构）、**交付时的汇报契约**（改了什么 / 为了什么 / 怎么验证 / 剩余风险）。

| 适合谁 | 典型诉求 |
| --- | --- |
| 用 AI agent 写生产代码的工程师 | 受够了 agent 造 `xxx_v2`、乱建 `utils2.py`、一次 PR 蔓延 20 个文件 |
| 需要 review AI 产出 diff 的人 | 希望 diff 小而聚焦，每行改动都有理由 |
| 功能开发 / bug 修复 / 重构 | 长链条任务中防止目标漂移、防止改错地方 |
| 团队协作仓库 | 让 agent 遵守项目既有惯例，而不是它自己的审美 |

**不适合**：纯文档编写、配置微调、非代码类问答（frontmatter 已明确排除）；也不适合想让 agent「自由发挥、一次改个痛快」的场景。

## 核心能力

| 能力 | 带来的结果 |
| --- | --- |
| 禁止平行实现 | 同一逻辑永远只有一份，杜绝「改了死代码、排查以天计」 |
| 动手前三次搜索 | 新功能先查是否已有实现，从源头消灭重复与双实现 |
| 外科手术式修改 | diff 只含任务要求改的部分，无关注释/格式/重构一律不动 |
| 定标 → 验证闭环 | 「完成」由可验证的成功标准定义，不是 agent 的自我感觉 |
| 复用有门槛 + 原则仲裁 | 提取公共代码要过三关准入；KISS/DRY/YAGNI/SOLID 打架时有优先级表可查 |

## 快速开始

### 安装

本 skill 遵循通用的 **Agent Skills 规范**（一个目录 + 一份带 frontmatter 的 `SKILL.md`），不绑定任何特定 agent。把目录放进你所用工具的 skills 目录即可：

```bash
git clone https://github.com/0xn0ne/skills.git
cp -r skills/coding/ <你的 agent 的 skills 目录>/
```

常见 agent 的 skills 目录：

| Agent | 用户级（全局可用） | 项目级（团队共享同一版本，推荐） |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/` | `<project>/.claude/skills/` |
| OpenCode | `~/.config/opencode/skills/` | `<project>/.opencode/skills/` |
| 其他支持 Agent Skills 的工具 | 按其文档指定的 skills 目录 | 同上（团队共享同一版本） |

> 不安装也能用：直接在 prompt 里给出 `SKILL.md` 的绝对路径，让 agent 加载即可。

自检（以 Claude Code 用户级为例）：`ls ~/.claude/skills/coding/SKILL.md`（应输出路径不报错）。触发方式：agent 依据 `SKILL.md` frontmatter 的 `description` 自动触发；也可在 prompt 中显式给出绝对路径加载。

### 最小调用（给 agent 的 prompt 模板）

```
你是一名遵守编码自律框架的工程师。

任务：[要开发的功能 / 要修的 bug / 要做的重构]
代码库：[绝对路径]

加载 SKILL（必须）：<你的 skills 目录>/coding/SKILL.md

严格按 SKILL.md 执行，尤其是「动手前三次搜索」和「外科手术式修改」。
完成后按 SKILL.md 的 5 项完成汇报契约输出。
```

### 预期输出

1. **代码改动** — 小而聚焦的 diff，只含任务范围内的修改。
2. **验证证据** — 跑过的测试 / lint / 复现步骤结果；没验证的要明说为什么。
3. **完成汇报**（5 项必填）— 改了什么 · 文件变更清单 · 为了什么 · 怎么验证 · 剩余风险与建议。

成功判据：代码能跑 + 定标时写下的成功标准全部满足 + diff 逐行自审无计划外文件、无调试残留。

## 工作流

```
┌─ 1 理解与侦察 ─┐ → ┌─ 2 定标 ─┐ → ┌─ 3 实施 ─┐ → ┌─ 4 验证 ─┐
│ 找现有实现     │    │ 可验证   │    │ 工程准则 │    │ 窄→宽测试│
│ 找唯一事实源   │    │ 成功标准 │    │ 任务清单 │    │ diff 逐行│
│ 找周围惯例     │    └──────────┘    │ 节点核对 │    │ 自审     │
└────────────────┘                    └──────────┘    └──────────┘
5 卡住时：同一问题 3 次失败即停止盲改；每次重试必须基于新假设，求助时汇报已排除的假设
```

**修 bug 的特殊纪律**：先复现拿到失败证据 → 确认要改的代码真的在执行路径上（不确定就故意抛错验证）→ 再修改。**改完现象毫无变化时，第一怀疑对象是「改错了地方」，而不是「改得不够多」。**

## 硬红线（无例外，违反即失败）

| # | 红线 | 为什么 |
| --- | --- | --- |
| 1 | 禁止平行实现（`xxx_v2` / `xxx_new` / `enhanced_xxx`） | 两份实现 → 后续修改有 50% 概率落在死代码上 |
| 2 | 发现双实现立即停止并报告 | 禁止自行挑一份改，更禁止制造第三份 |
| 3 | 秘密不落盘 | 密码 / 密钥 / token 绝不进版本控制 |
| 4 | 不可逆高危操作先获确认 | force push、删分支、`rm -rf`、drop table、改生产环境 |
| 5 | 禁止静默吞错 | 内部纯逻辑不许 try/except 包裹，bare except 是最严重违规 |

## 工程准则（启发式：默认遵循，有更好理由可偏离）

| 准则 | 一句话要点 |
| --- | --- |
| 恰到好处的工程 | 只实现被要求的功能；单一实现不建 interface；无测量数据不做性能优化 |
| 结构纪律 | 编辑优先于新建；**行数不是拆分理由**，职责混杂才是；禁止「一类一文件」 |
| 复用有门槛 | 标准是**领域无关性**，不是被 import 的次数；common 里出现业务词汇即违规 |
| 暴露优于掩盖 | 错误处理只放在真正的外部边界（网络 / IO / 子进程 / 用户输入） |
| 外科手术式修改 | 不顺手重构；童子军军规收窄到「你本来就要触碰的行」 |

- 新建文件判定 · 公共代码准入测试 · 重复实现处置 · 抽象时机（Rule of Three）→ [`./references/code-organization.md`](./references/code-organization.md)
- 原则打架时听谁的（一致性 > 可读性 > YAGNI > KISS > 外科手术 > 显式失败 > 组合 > 测量）→ [`./references/principle-tradeoffs.md`](./references/principle-tradeoffs.md)

## 授权边界

| 层级 | 事项 |
| --- | --- |
| **自由决定** | 实现细节、算法选择、局部命名、既有文件内的代码组织；删除本次改动直接产生的死代码 |
| **说明理由再动手** | 新增文件/目录/依赖、提取公共代码、改函数签名、超出任务范围的重构、DB schema 变更 |
| **必须停下来问** | 需求有多种合理解释、发现任务本身可能是错的、要删改不完全理解的代码、触发任一硬红线 |

## 输入 / 输出契约

| 方向 | 项 | 必填 | 说明 |
| --- | --- | --- | --- |
| 输入 | 任务描述 | ✓ | 新功能 / bug 修复 / 重构 |
| 输入 | 代码库路径 | ✓ | agent 需读到真实代码才能做动手前侦察；成功标准未给出时在「定标」阶段自定 |
| 输出 | 代码改动 | ✓ | 源码 diff（路径由任务决定，本 skill 不规定产物路径） |
| 输出 | 完成汇报 | ✓ | 5 项固定契约：改了什么 / 文件变更清单 / 为了什么 / 怎么验证 / 剩余风险 |

## 使用场景 / Anti-Patterns

| 反模式 | 为什么坏 |
| --- | --- |
| 跳过侦察直接写代码 | 制造重复实现，后续所有修改都可能落在死代码上 |
| 改完现象没变就继续叠加改动 | 大概率改错了地方；应回到执行路径验证 |
| 建 `utils2.py` / `helpers.py` 这类垃圾抽屉 | 按技术动作碎片化，职责无处安放 |
| 把被多次 import 的业务函数挪进 common | 流行度 ≠ 通用性，业务规则散落到无人认领的地方 |
| 内部纯逻辑包 try/except、加 fallback | 掩盖本应修复的问题，把一次性成本变成长期排查成本 |
| 顺手重构任务范围外的代码 / 重试 3 次仍盲改 | 违反外科手术纪律、diff 膨胀；卡住时应停止并汇报已排除的假设 |
