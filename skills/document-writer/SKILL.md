# document-writer

## 0. 存在意图（为什么有这个模块）

你要产出的是一份**有论证的文档**，而不是"标题 + 表格 + 项目符号"堆成的信息卡片。

一份及格的报告，读者遮住所有表格后仍应能理解：结论是什么、为什么成立、对他/她意味着什么、下一步做什么。表格的作用是**加速比较和查找**，不是**替代思考**。

如果你在起草时发现"离开表格就写不出内容"，这是内容深度不足的信号，不是形式问题——应补充分析，而不是让表格顶上。

---

## 1. 冲突解决优先级（自上而下裁决）

当规则之间张力时，按以下顺序裁决：

1. 用户明确要求
2. 事实准确性与证据完整性
3. 论证完整性与叙事连贯性
4. 文体和受众适配
5. 简洁、易读与版式美观
6. 表格、列表等视觉形式

> 注：本模块"正文优先于表格"的取向属于第 3 层的具体化。当用户明确要求"给我一个纯表格对照"或任务本质是数据目录/审计清单等表格密集文档时，遵循用户与文体（见 §7 边界文体条款），不适用本模块的默认表格数量限制。

---

## 2. 三区划分：红线 / 启发式 / 自主判断

为避免歧义导致的过度收紧，本模块所有规则分为三类，其权重不同：

### 🔴 红线（RED_LINES）——违反即失败，无自主裁量空间

R1. **章节标题后不得直接出现表格**。标题与表格之间必须有章首说明段。
R2. **章节不得以无解读的表格结束**。表格后必须有解读段。
R3. **正文中不得连续出现两张表格**。中间必须有过渡说明。
R4. **不得为满足结构、标题格式或"看起来专业"而捏造结论、数字或因果关系**。
R5. **不得在最终交付物中输出内部规划、章节地图、自检清单等元话语**。
R6. **表格不得承担因果解释、论证过程或推荐理由的核心表达**——这些必须在正文段落中完成。
R7. **不得出现"仅标题 + 表格 / 列表"、无正文段落的章节**（附录、数据字典、术语表除外）。

### 🟡 启发式（HEURISTICS）——默认遵循，允许在合理理由下偏离并简要说明理由

H1. 结论/发现/建议类章节优先用**结论型标题**；背景/范围/方法类章节允许**描述型标题**。
H2. 主体段落默认采用"判断 → 证据 → 解释 → 意义 → 连接"五段式论证链，但不要求机械套用。
H3. 常规文档每个主要章节默认不超过 1 张表格；出现第 2 张必须回答不同问题。
H4. 章首说明通常 2—4 句；章节收束通常 1—2 句。
H5. 一维并列信息优先项目符号；有先后顺序的信息优先编号列表；需要"为什么"的必须段落。
H6. 大规模来源矩阵、原始数据优先入附录，正文只留关键证据与解释。

### 🟢 自主判断区（AUTONOMOUS）——你自己决定，不要因不确定而保守收紧

A1. **具体章节数量与命名**：只要覆盖了文体所需回答的问题，可自行合并、拆分、增加、删除章节。
A2. **段落长度与数量**：以"一段一中心问题"为准，不设字数限制。
A3. **示例、类比、修辞的使用**：在保持准确性前提下由你判断是否使用及使用密度。
A4. **列表 vs 段落 vs 表格的具体选择**：只要通过 §6 的准入测试与三明治要求，选择方式由你决定。
A5. **文档整体风格与语气**：根据受众和文体自行校准（例如高管摘要偏简洁、技术评估偏严谨）。
A6. **是否使用小节、加粗、引用块等版式元素**：服务于可读性即可。

> 遇到本文未覆盖的模糊情况，默认按"意图对齐"处理：回到 §0 的存在意图与 §1 的优先级列表推断应做什么，而不是卡住或保守缩水。

## 3. 文体 → 默认结构映射

用户指定结构时优先遵守用户结构。未指定时按文体选择默认骨架（可按 A1 调整）。

| 文体 | 默认骨架 |
| --- | --- |
| 分析 / 研究 / 评估 / 决策报告 | 执行摘要 → 主要发现 → 洞察与跨领域分析 → 风险与红队分析 → 结论与后续步骤 |
| 方案 / 提案 / 规划 | 背景与问题 → 目标/范围/约束 → 核心方案与依据 → 备选方案与取舍 → 实施路径/资源/里程碑 → 风险与决策请求 |
| 工作 / 进展 / 专题汇报 | 目标与本期结论 → 已完成工作与结果 → 关键变化与原因 → 当前问题与影响 → 需要的决策或支持 → 下一阶段安排 |
| 总结 / 复盘 / 阶段回顾 | 原目标与范围 → 实际完成情况 → 结果与差距 → 原因分析 → 经验与教训 → 后续改进与责任 |

**关键约束**：不得为保留固定章节而生成空洞、重复或只能用表格填充的章节——空章节应删除或合并。

---

## 4. 起草前的内部准备（不输出）

正式起草前，在内部（不写入最终文档）明确：

- 围绕核心内容明确全文最重要的一句话；
- 读者读完要知道 / 相信 / 决定什么；
- 每个章节要回答哪个问题、核心判断是什么、需要哪些证据；
- 每处内容最适合段落、列表、表格还是附录（默认段落，通过 §6 准入才用表格）；
- 章节之间的逻辑关系（见 §5）。

**为什么内部准备重要**：这是"意图对齐"和"抗漂移"的锚点。跳过这一步会导致边写边想、章节脱节、结论漂移。

---

## 5. 每个主要章节的叙事单元

每个一级或二级章节（附录 / 数据字典 / 术语表 / 用户明确要求的纯表格输出除外）由四部分构成：

**5.1 标题**（H1）——结论型或描述型，见启发式条款。禁止为凑格式而捏造结论（R4）。

**5.2 章首说明**（红线：R1、R7）

- 目的：让读者立刻知道本节要回答什么、为什么重要、和上一节什么关系。
- 反例："本节将对相关方案进行分析。""具体情况如下。""下面通过表格进行说明。"
- 正例："要判断该方案能否按期上线，需同时考察开发周期、人员依赖和迁移风险。现有证据表明纯自研虽成本较低，但无法消除核心人员单点依赖，因此本节重点比较三种方案的交付可控性。"

**5.3 主体段落**（H2）

- 默认论证链：**判断 → 证据 → 解释 → 对读者的意义 → 与下段/下节的连接**。
- 每段处理一个中心问题；段落首句应让读者知道"这一段为什么存在"。
- **禁止只堆事实、只列数据或只下结论而不解释**。

**5.4 章节收束**（H4；红线：R2）

- 至少完成其中一项：总结本节最重要含义 / 给出决策或行动 / 指出未解决问题 / 引出下一节。

---

## 6. 衔接：用真实逻辑关系，不是过渡词

衔接的目的是**说清前后内容的关系**，不是撒"此外、同时、因此"。写作时明确判断当前属于哪种关系：

因果 / 转折 / 递进 / 条件 / 对比 / 问题—回答 / 结论—行动

优先"旧信息 → 新信息"的推进方式：先承接读者刚读到的概念，再引入新判断。**不得为衔接而虚构因果**（R4 的延伸）。

---

## 7. 表格治理（合并原准入 / 三明治 / 数量 / 删除测试）

### 7.1 准入测试——同时满足以下才可在正文使用表格

1. 信息具有真实、稳定的行列关系；
2. 读者确实需要横向比较或查找精确值；
3. 段落或列表会明显降低查找和比较效率；
4. 各行各列语义结构平行一致；
5. 单元格可用数字、短语或短句表达（不出现整段落）；
6. 表格与正文结论直接相关；
7. 表格保持简单，不依赖复杂合并单元格或多层表头。

任一不满足，改用段落 / 列表 / 附录。

**典型适合**：多方案同维度比较、基准测试结果、精确统计数据、执行矩阵（时间×责任人×交付物）、参数/口径清单。
**典型不适合**：章节摘要、因果链、推荐理由、战略判断、一两个简单事实、单维列表、流程步骤、每格需一段话的内容。

### 7.2 表格三明治（红线：R1、R2）

每张表格必须由三部分组成：

- **表前说明段**：这张表回答什么问题、比较哪些对象和维度、数据范围/时间/口径、读者应重点观察什么。
- **表格本身**：清晰标题、具体列名、必要的单位/时间/来源/认知地位标注、平行一致的单元格。
- **表后解读段**：指出 1—3 个最重要的模式/差异/异常 → 解释为什么 → 说明对结论或行动的意义 → 必要时说明数据限制 → 引出下一步。**不逐行复述表格数据**。

### 7.3 数量默认（启发式：H3）

- 允许全文零表格；
- 每主要章节默认 ≤ 1 张；
- 同章节第 2 张必须回答不同问题；
- 不得连续两张表格（R3）；
- 不得为提高"数字密度"而重复展示相同数据。

### 7.4 边界文体条款（补齐鲁棒性）

以下文体天然表格密集，本节数量默认不适用，但三明治要求（7.2）与准入测试（7.1）仍适用：

- 数据目录 / 数据字典 / 参数手册
- 审计清单 / 合规核查表
- 基准评测（benchmark）报告的结果章节
- 用户明确要求以表格为主体的对照材料

处理方式：正文提供**总说明段 + 关键发现解读段**，表格集中呈现，不再要求"每章 ≤ 1 张"。

### 7.5 表格删除测试（自检项，见 §9）

完稿后暂时隐藏全部表格，读者仍应能从标题和段落中理解核心结论、关键原因、影响、建议行动。如做不到，补正文而不是要求读者自行解读表格。

---

## 8. "答案先行"的正确理解

答案先行 = 先给判断再给依据、先说结论再展开分析、先告诉读者为什么值得继续读。

答案先行 ≠ 因为标题/摘要/表格已经"说过"结论，正文可以省略解释。

**四者不可互相替代**：标题负责导航，章首段负责定向，主体段落负责证明，章节结尾负责收束与连接

## 9. 交付契约（DONE_WHEN，可独立核查）

以下每项都必须为"是"才允许交付。任何一项"否"，重写对应部分。

### 结构契约

- [ ] 每个非附录主要章节都包含"标题 + 章首说明 + 主体段落 + 收束"四部分
- [ ] 所有表格都被"说明段 + 表格 + 解读段"包裹
- [ ] 不存在"标题紧接表格"的情况
- [ ] 不存在以无解读表格结尾的章节
- [ ] 不存在连续两张表格
- [ ] 不存在"仅标题 + 表格/列表"的章节（附录除外）

### 内容契约

- [ ] 每个结论型标题都在对应正文中给出了证据和推理，而不仅停留在标题
- [ ] 每张表格都通过 §7.1 的 7 条准入测试
- [ ] 隐藏全部表格后，正文仍能独立传达核心结论、关键原因、影响、建议
- [ ] 所有结论、数字、因果关系可追溯到证据，不存在为格式凑出的内容
- [ ] 最终文档中不含内部规划、章节地图、自检清单等元话语

### 交付契约

- [ ] 输出仅包含最终文档本身，不附加过程性说明（除非用户明确要求）

## 10. 参考示例（简版）

### ❌ 错误：标题 + 表格，无叙事

> ## 方案比较
>
> | 方案 | 周期 | 成本 | 风险 |
> | --- | --- | --- | --- |
> | 自研 | 较长 | 低 | 高 |
> | ... | ... | ... | ... |

问题：违反 R1（标题后直接表格）、R6（表格承担了推荐理由）、R7（无正文段落）。

### ✅ 正确：结论型标题 + 章首说明 + 表格 + 解读 + 收束

> ## 推荐混合方案：在交付进度与依赖风险之间取得更好平衡
>
> 在上线时间固定、且不能接受核心人员单点依赖的前提下，混合方案比纯自研更可控，也比完全采购保留了更多调整空间。本节比较三种方案的交付周期、持续成本和主要风险；表 1 用于压缩可比信息，最终推荐取决于表后的风险解释。
>
> **表 1：三种实施方案的核心差异**
>
> | 方案 | 交付周期 | 持续成本 | 主要风险 |
> | --- | --- | --- | --- |
> | 自研 | 较长 | 较低 | 核心人员依赖 |
> | 采购 | 较短 | 较高 | 供应商锁定 |
> | 混合 | 中等 | 中等 | 接口与责任边界 |
>
> 三种方案不存在所有维度都占优的选择。纯自研的真正问题不是初始成本，而是关键人员依赖直接影响交付确定性；完全采购虽然更快，却增加后续切换成本。混合方案的优势是风险更可拆分——因此建议核心能力自研、非核心模块采购，并在项目启动前明确接口和责任边界。
>
> 这一选择解决了技术路径问题，但尚未回答实施资源是否充足。下一节据此评估人员投入、预算和里程碑安排。
