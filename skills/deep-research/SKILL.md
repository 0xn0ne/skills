# Deep Research

## 1. 意图：这个技能为什么存在

研究的目的不是穷尽资料，而是**在有限成本内达到"足以让用户放心行动"的证据质量**。
所有规则都服务于三个效果：

1. **结论可信**——关键主张锚定到可核查的来源，而非 agent 的语感；
2. **反方诚实**——结论经过认真的证伪尝试，不确定就明说，"待定"是合法结论；
3. **读者能行动**——30 秒抓到结论，知道下一步是什么、谁来做、什么条件下要反悔。

**规则未覆盖或互相冲突时，回到这三条判断该怎么做。** 步骤是意图的实现，不是意图本身。

## 2. 红线（违反即任务失败，无例外）

其余一切都是启发式，唯独以下 5 条是硬约束：

1. **数据保真**：报告声称使用了工具持久化数据（claims/rounds/假设追踪），ledger 里就必须
   真实存在。数据未持久化 = 数据未存在。audit 未通过时必须三选一（见 §7），
   **沉默交付 = 违反诚实底线**。
2. **数字必须有据**：无来源的数字不得出现在报告中，宁写"未获得数据"。
3. **引用不可捏造**：每个 [S#] 必须对应真实访问过的来源；不为凑格式编造引用。
4. **假设改判需外部证据**："无效/修正"只能由外部来源触发；"我重新想了想"不能改状态。
5. **高风险结论必须带边界**：涉及大额资金、法律、医疗、安全或不可逆选择的建议，
   必须显式标注不确定性、反悔条件（Holds/Reverts）与"什么证据会推翻本结论"。

工程约束（防数据丢失）：**同一 ledger 上的 CLI 调用必须串行**，等前一个完成再发下一个。

## 3. 你的自主区（显式授权，无需请示）

以下事项由你自主判断，做了就记录理由（一行即可），不要因为"没有规则"而收紧：

- 搜索策略：probe 的类型、顺序、数量（硬上限内）、查询词、pivot 时机
- 工作量升降级（L1↔L2↔L3）与提前停止
- 报告章节权重、Cross-Domain 写什么、结论如何措辞
- 用户额外要求的内容（代码/时间线/TCO...）放进哪个位置、以什么形态呈现
- 是否向用户问澄清问题（上限 3 个，只问会改变研究计划的）
- 参考文件加载时机（按 §8 的路由建议，但你可以基于任务判断偏离）

默认姿态：**拿不准时，行动并记录假设，而不是停下来等指示。**

## 4. 流程：Frame → Dig → Decide

### 4.1 Frame：任务卡（第一动作，唯一权威模板）

**第一件事**：确认工作目录。用 `pwd` 看当前目录，然后在该目录的 `research/` 子目录下存放所有产出物（报告写入 `research/`，脚本会把 ledger 写入 `research/.cache/`）。**不要 cd 到其他目录后再运行工具**——`research_tools.py` 基于 CWD 定位文件，cd 后 ledger 和报告会分离，`inline` 注入会失败。Frame 阶段用 `suggest-path --mkdir <topic>` 一次性创建目录并确认路径。

```markdown
## 任务卡

- 用户目标：最终要做什么决定 / 获得什么认知 / 采取什么行动
- 决策后果：低 / 中 / 高（错误答案的代价？是否涉及钱/法律/医疗/安全/不可逆？）
- 任务类型（primary_lens，必填）：决策 / 比较 / 证据综述 / 现状扫描 / 基准评测 / 探索
- 副类型（secondary_lens，0-2 个）：
- 受众：决策者（默认）/ 实务人员 / 研究者 / 混合
- 范围边界：时间 / 地理 / 行业 / 预算 / 排除项
- 初始假设（≥2 条互斥，含"主张为假"版本）：H1 / H2 / (H3)
- Must-have 标准（研究完成的验收清单）：
  - [ ] ...
- 反方条件：什么证据会推翻或重写初始判断
- 工作量：L1 快速 / L2 标准 / L3 复杂（probe 2-5 次后定，可中途升降级）
```

lens 判别拿不准时的 5 个边界问题见 `references/report-rendering.md`；仍答不上 → 默认"决策"。
澄清问题 ≤3 个且默认假设足以继续时不阻塞。

### 4.2 Dig：probe-search（方法细节见 `references/probe-search.md`）

**计量单位，全文只有这一处定义：**

- **round** = 1 次成功的搜索工具调用（工具按此计数，硬上限：L1=20 / L2=50 / L3=80）
- **probe** = 1 次有明确目的的信息动作（通常含 1-10 个 round + 阅读 + 判断；按 probe 规划节奏，按 round 检查上限）

**每轮记录（JSON key 与工具完全一致）：**

| key | 本轮回答的问题 |
| --- | --- |
| 新检测 | 是否补齐了 Must-have 证据缺口？ |
| 新深度 | 是否把关键主张升级到更高级来源？ |
| 新比较 | 是否发现或解决了来源冲突？ |
| 新视角 | 是否可能改变结论、推荐或排序？ |
| 新维度 | 是否发现新的边界条件、约束或风险？ |

Sum ≥ 1 = 有推进；Sum = 0 → 下一 probe 必须 pivot；连续 2 轮 Sum=0 且无高风险未决项 → 进 Decide。

**停止条件（唯一权威表，满足任一即进 Decide）：**

| # | 条件 | 判定者 |
| --- | --- | --- |
| S1 | 任务卡 Must-have 全部满足 | 你（勾 checklist） |
| S2 | 主要分歧已解决，或已标为"未决且不影响当前行动" | 你 |
| S3 | 颠覆性反证出现，假设转"无效"，任务需 reframe | 你 |
| S4 | 达到 round 硬上限 | `research_tools.py check-stop --effort L?` |
| S5 | 连续 2 probe 零增益且无高风险未决项 | 你 |
| S6 | 缺用户偏好/预算/约束，继续搜索无效 → 问用户 | 你 |
| S7 | 依赖的最新状态无法验证 → 带不确定性输出 | 你 |

### 4.3 Decide：报告

- 默认 5 章：ES / Key Findings / Insights & Cross-Domain / Risks & Red Team / Conclusions。
  lens 只调章节**深度**，不增减章节；Cross-Domain 是 Insights 的固定子模块，
  深度随 lens 从"一句话"到"重头戏"，内容由你自主发挥。
- 用户明确要求的额外内容（代码/时间线/方案...）：位置和形态由你定（自主区），
  质量优先于结构合规。用户没要求就严格 5 章。
- 章节权重表、受众适配、写作技法见 `references/report-rendering.md`。
- 输出位置：默认 conversation；写文件时用 `suggest-path` 取规范路径（`research/` 下，别处不写）。

## 5. 条件启用模块

| 模块 | 启用条件 | 见 |
| --- | --- | --- |
| 竞争假设 + 4 态追踪 | primary_lens ∈ {决策, 比较, 证据综述, 探索} | `references/hypothesis-redteam.md` |

## 6. 工具（`scripts/research_tools.py`，全部串行调用）

> 工具基于 **CWD** 定位 `research/`。所有命令在同一 CWD 下运行——ledger 和报告必须在同一个 `research/` 下，否则 `inline` 注入会找不到 ledger。
>
> 同目录下有多个调研时，后续命令用 `--topic <slug>` 选定 ledger。`list` 查看可用 topic。`setup` 输出的 slug 就是 `--topic` 的值。

| 时机 | 命令 |
| --- | --- |
| Frame 完成 | `setup <topic> [H1 主假设] [高/中/低]` |
| 每个来源 | `source S# <url> --tier 一手/二手/传闻 --title --date` |
| 每轮搜索后 | `round <n> '{"新检测":"Y",...}' [summary]` |
| **Dig 阶段**·每条事实 | `claim "<text>" 已确认/已公开/自推断/未验证/auto --sources S1,S2` |
| 标签拿不准 | `suggest-label --sources S1,S2` |
| 假设状态变化 | `hyp 有效/修正/无效/待定 高/中/低 <触发证据> [S#] [原因]` |
| 检查是否该停 | `check-stop --effort L1/L2/L3` |
| **Decide 阶段**·每个章节锚点 | `finding "<结论句>" --claims C1,C2,C3` |
| 写报告前 | `claims-dump`（按 4 档分组 + findings 映射，可直接拼入报告）+ `audit` |
| 最终决定 | `decide YES/NO/DEFER [建议] [边界]` |
| 报告写完 | `inline --write <file.md>`（注入引用元数据）→ 快速复核 |

**claim 与 finding 的关系**：
- **`claim` = 事实砖块**（Dig 阶段）。每条可验证的单一事实主张，带认知标签 + 来源。原子级。
- **`finding` = 砖块砌成的墙**（Decide 阶段）。多条 claim 综合出的结构性结论，对应报告 Key Findings 的一个**章节**。每个 finding 用 `--claims C1,C2,C3` 关联支撑它的 claim IDs。
- 工作流：先在 Dig 阶段逐条记 claim → 进入 Decide 时把相关 claim 组合成 finding → 报告 Key Findings 章节下每个小节 = 一个 finding，内文引用支撑它的 claim。

竞争假设的持久化：主假设用 `hyp` 追踪；替代假设（H2/H3）各记一条
`claim "H2: ..." 自推断`，状态变化时更新 claim 并在报告追踪表中呈现。

## 7. 交付门：8 项自检（唯一权威版本，DELIVER 前逐项过）

1. ☐ 30 秒复述测试：只读标题+首段能否复述结论
2. ☐ 动词主导开篇（建议/拒绝/升级，不铺垫）
3. ☐ 数字密度符合 lens 且每个数字有来源（红线 2）
4. ☐ 边界条件 ≥1 组 Holds/Reverts
5. ☐ YES/NO/DEFER 显式（决策类 lens 强制）
6. ☐ 反方诚实：Red Team 打过 + Steel-man 过最强反方
7. ☐ 可执行：Who / What / When
8. ☐ 工具数据保真：跑 `audit`，达到其输出的通过阈值

**第 8 项失败 → 三选一，然后才能交付：**

- 回填 ledger（推荐）：把关键 claims/rounds/hyp 补写入，再出报告
- DELAY：告知用户"工具记录不完整，先给简要答复，稍后补完整报告"
- 声明降级：报告末尾显式写"本报告未通过工具保真验证，基于会话内推理，仅供参考"
