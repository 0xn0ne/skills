# cli-design —— CLI 接口设计与治理

> 把 CLI 当作**发布即承诺的公共契约**来设计：新增命令前先盘点、命名全局一致、弃用有始有终。为 CLI 加/改任何用户可见接口（含隐藏标志）之前加载。

## 这是什么 / 给谁用

**不是**：拍一个 `app dump-users --csv` 就提交的实现型改动。**而是**：一套 CLI 接口设计与治理规范——先判断契约强度，再按五条红线推进，最后用 DONE_WHEN 清单验收。

| 角色 | 典型场景 |
| --- | --- |
| CLI 工具作者 | 要新增子命令或标志，怕接口越加越乱 |
| 平台 / 基础架构工程师 | 内部 CLI 被 CI 脚本依赖，改动需破坏性评估 |
| Reviewer / 技术负责人 | 评审时发现「两个命令 70% 重叠」却说不清该合并哪个 |
| 存量 CLI 维护者 | 仓库里没有接口清单，需要先从现状反推一份规范 |

**不适合**：纯业务逻辑实现（不涉及用户可见接口）、GUI/TUI 交互设计、REST API 设计。

---

## 核心能力

- **接口盘点先行** — 添加任何命令/标志前先产出重叠分析，与现有命令重叠过半时默认「扩展而非新增」
- **契约强度分级** — 先判断「有没有你控制不了的调用方」，决定弃用红线松紧；低强度下强制「直接改 + 同变更内迁移」
- **选型决策链** — 子命令 / 标志 / 位置参数 / 环境变量按决策顺序判定，含「必填的标志其实是动作」等纠正信号
- **弃用生命周期 + 单一事实源** — 旧接口四要件（警告 / 隐藏 / 登记 / 转发别名），`docs/cli-spec.md` 与代码同提交同步

## 快速开始

### 安装

本 skill 遵循通用的 **Agent Skills 规范**（一个目录 + 一份带 frontmatter 的 `SKILL.md`），不绑定任何特定 agent。把目录放进你所用工具的 skills 目录即可：

```bash
git clone https://github.com/0xn0ne/skills.git
cp -r skills/cli-design/ <你的 agent 的 skills 目录>/
```

常见 agent 的 skills 目录：

| Agent | 用户级（全局可用） | 项目级（团队共享同一版本，推荐） |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/` | `<project>/.claude/skills/` |
| OpenCode | `~/.config/opencode/skills/` | `<project>/.opencode/skills/` |
| 其他支持 Agent Skills 的工具 | 按其文档指定的 skills 目录 | 同上（团队共享同一版本） |

> 不安装也能用：直接在 prompt 里给出 `SKILL.md` 的绝对路径，让 agent 加载即可。

自检（以 Claude Code 用户级为例）：`ls ~/.claude/skills/cli-design/SKILL.md`

触发方式：由 agent 依据 [`./SKILL.md`](./SKILL.md) frontmatter 的 `description` 自动触发——凡是要向 CLI 添加或修改用户可见接口（含隐藏标志）时命中；也可在 prompt 中显式给出绝对路径加载。

### 最小调用（给 agent 的 prompt 模板）

```text
我要给 <CLI 名称> 增加「导出用户数据为 CSV」的能力。
CLI 源码路径：<仓库/目录绝对路径>

加载 SKILL 并严格执行：<你的 skills 目录>/cli-design/SKILL.md

要求：
1. 先判断契约强度（有没有我控制不了的调用方），判断不了就问我；
2. 按红线 R1 做接口盘点与重叠分析，结论必须是「扩展现有命令」或「新增 + 为什么扩展不可行」；
3. 同步更新 docs/cli-spec.md（不存在则先生成）；
4. 交付前逐条过 DONE_WHEN 清单。
```

> prompt 里不要复述 SKILL 正文规则，只给需求 + 路径 + 要求，否则会稀释 skill 自身的约束力。

### 预期输出

| 产出 | 位置 / 形式 | 成功判据 |
| --- | --- | --- |
| 契约强度 + 重叠分析 | 回答中 | 已判定高/低（或已提问）；列出最相近的 1-3 个现有命令，结论为「扩展」或「新增 + 理由」 |
| 接口改动 + help | 源码 | 新名字有长名、无近义冲突、术语与词表一致；`app -h`、`app <sub> --help` 均可运行且含新接口示例 |
| 接口注册表 | `docs/cli-spec.md` | 命令树 / 术语表 / 弃用台账与代码同一提交 |

## 工作流

```text
┌─ 第 0 步：契约强度 ─┐   ┌─ 选型 ──────────────────┐   ┌─ 落地 + 验收 ─────┐
│ 有外部调用方？      │   │ 1 不同动作/对象 → 子命令 │   │ 写 3-5 条用法示例 │
│  是→高（弃用红线）  │ → │ 2 修饰同一动作 → 标志    │ → │ help 全覆盖       │
│  否→低（直接改+迁移）│   │ 3 核心对象 → 位置参数    │   │ 同步 cli-spec.md  │
│ 判断不了 → 问用户   │   │ 4 其余 → 环境变量/配置   │   │ 过 DONE_WHEN      │
└────────────────────┘   └──────────────────────────┘   └───────────────────┘
```

### 选型决策顺序

| # | 判断问题 | 结论 |
| --- | --- | --- |
| 1 | 是不同的动作或不同的操作对象吗？ | 子命令（对象多 + 动作多时用 noun-verb 两级，层级最多两级） |
| 2 | 是在修饰同一动作的行为方式吗（开关/程度/格式/环境）？ | 标志（若该标志必填或改变其余参数语法 → 其实它是动作，改回子命令） |
| 3 | 是该动作的核心操作对象吗？ | 位置参数（尽量只有一类；两类以上不同含义 → 次要的改为标志） |
| 4 | 都不是（部署配置、密钥等） | 环境变量或配置文件，不进命令行 |

### DONE_WHEN 验收清单

- [ ] 重叠分析已输出，结论是「扩展」或「新增 + 理由」之一
- [ ] 新名字通过命名检查：有长名、无近义冲突、术语与词表一致
- [ ] 若删/改了已发布接口：弃用台账已登记，旧入口是转发别名而非逻辑副本
- [ ] `docs/cli-spec.md` 与代码在同一提交中一致
- [ ] 全部 help 路径可运行且包含新接口的示例
- [ ] 破坏性命令有确认 / `--force` / `--dry-run`

## 输入 / 输出契约

| 方向 | 项 | 必填 | 说明 |
| --- | --- | --- | --- |
| 输入 | 变更需求 | ✓ | 要新增/修改哪个用户可见接口，解决什么问题 |
| 输入 | CLI 源码路径 | ✓ | 供遍历命令定义或运行 `--help` 树做接口盘点 |
| 输入 | `docs/cli-spec.md` | × | 不存在时第一个任务是从现状生成它 |
| 输入 | 契约强度 | × | 高 / 低；判断不了时必须提问，这一个问题值得打断 |
| 输出 | 接口注册表 | ✓ | `docs/cli-spec.md`：命令树 + 术语表（动词表/名词表）+ 弃用台账（deprecated on / remove by / 替代品） |

## 红线速览

细节见 [`./SKILL.md`](./SKILL.md)，此处只做索引：

| # | 红线 | 一句话 |
| --- | --- | --- |
| R1 | 先盘点，后新增 | 重叠过半 → 默认扩展现有命令，新增须写明扩展为何不可行 |
| R2 | 命名一致性 | 强制长名；同一概念一个词；业界惯用名沿用；禁止近义命令名并存 |
| R3 | 变更走生命周期 | 禁止静默删除/改语义，也禁止无限期保留未标记旧接口 |
| R4 | 单一事实源 | `docs/cli-spec.md` 与代码同提交同步 |
| R5 | 破坏性操作防护 | 默认需确认，提供 `--force` / `--yes`，尽量提供 `--dry-run` |

## 不适用 / Anti-Patterns

| 反模式 | 为什么坏 | 怎么做 |
| --- | --- | --- |
| 不读接口清单就新增命令 | 产生「两个命令 70% 重叠」，接口面膨胀 | 先做重叠分析，能加标志解决就不加命令 |
| 给一次性内部命令走 N+2 弃用周期 | R3 的意图是保护外部契约，该命令根本不进入契约 | 标记 hidden + 在 cli-spec.md 登记为 experimental 并写明删除条件 |
| 低契约强度下保留旧接口 | 保留只在有外部调用方时是美德，否则是垃圾堆积 | 直接改，并在同一变更内全量迁移调用点 |
| 旧接口复制一份逻辑继续维护 | 行为漂移，双份实现双份 bug | 旧入口做成新接口的别名/转发 |
| 先写代码再想用法 | 别扭的语法一旦发布就是永久承诺 | 先写 3-5 条真实使用示例，念着别扭就不实现 |
