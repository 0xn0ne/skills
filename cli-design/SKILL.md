# CLI 接口设计与治理

## 你要达成什么（意图，优先级高于一切步骤）

CLI 是一份**发布即承诺的公共契约**，和 REST API 同级：用户会把它写进脚本、写进文档、写进肌肉记忆。因此本 skill 的全部规则服务于三个目标：

1. **一个功能只有一个入口**——接口面最小化，杜绝"两个命令 70% 重叠"。
2. **可预测性**——用户见过一个子命令，就能猜出其他子命令的形态；见过一个标志名，就能在别处复用这个记忆。
3. **可演化性**——接口能安全地迭代：加法优先，弃用有始有终，僵尸命令有看门人。

当下面的规则覆盖不到你遇到的情况时，回到这三个目标做判断，并在产出中简述你的推理。不要因为"没有规则"而卡住或擅自收紧。

## 第 0 步：先判断契约强度（决定后面所有规则的松紧）

动手前先回答：**这个 CLI 有没有你控制不了的调用方？**

- 有外部用户 / CI 脚本 / 其他团队依赖 → 契约强度=高，弃用红线全部生效。
- 纯内部、调用方全部在本仓库可搜索 → 契约强度=低，破坏性变更的正确做法是"直接改 + 同一个变更内全量迁移调用点"，**不允许**为省事保留旧接口。（保留旧接口只在高契约强度下是美德，在低强度下是垃圾堆积。）

判断不了就问用户，这一个问题值得打断。

## 红线（MUST，违反即任务失败）

R1. **先盘点，后新增。** 添加任何命令/子命令/标志前，必须先读取接口清单（`docs/cli-spec.md`，见 R4；没有就现场生成：遍历源码中的命令定义或运行 `--help` 树）。产出一份简短重叠分析：列出功能最相近的 1-3 个现有命令。若新功能与现有命令的输入输出或职责重叠超过约一半，默认方案是**扩展现有命令（加标志/加参数）而非新增命令**；确要新增，必须在提交说明中写明为什么扩展不可行。
R2. **命名一致性。**
    - 每个标志必须有 `--long-name` 长形式；单字母短名只分配给高频标志，且分配前必须检查全 CLI 无冲突、不与业界惯例冲突。
    - 同一概念全 CLI 只用一个词（timeout 就是 timeout，不允许另一处叫time/wait/duration）。新词条以 cli-spec.md 的术语表为准。
    - 业界有惯用名的必须沿用：-h/--help、--version（不是 -v）、-v/--verbose、-q/--quiet、-f/--force、-o/--output、--json、--dry-run。
    - 禁止新增与现有命令近义的命令名（update/upgrade、remove/delete/rm并存即违规；选定一个动词后全 CLI 统一）。
R3. **接口变更必须走生命周期，禁止两种极端。**
    高契约强度下：
    - 禁止静默删除或改变任何已发布接口的语义。
    - 禁止无限期保留未标记的旧接口。保留旧命令/旧标志必须同时满足：
      (a) 使用时打印弃用警告并指出替代品；(b) 从 help 中隐藏；
      (c) 在 cli-spec.md 登记弃用版本和计划移除版本（默认 N+2 或 90 天，取较晚者）；(d) 实现上是新接口的别名/转发，禁止复制一份逻辑。
    低契约强度下：直接改，并在同一变更内迁移所有调用点，不留旧接口。
R4. **单一事实源。** `docs/cli-spec.md` 是接口注册表，记录：命令树、每个标志的名字与含义、术语表（动词表+名词表）、弃用台账（deprecated on / remove by / 替代品）。任何接口变更必须在同一次提交中同步更新它。该文件不存在时，你的第一个任务是从现状生成它。
R5. **破坏性操作防护。** 删除数据、覆盖文件、不可逆动作的命令必须默认需要确认，提供 `--force`/`--yes` 供脚本使用，并尽量提供 `--dry-run`。

## 选型决策规则（子命令 vs 标志 vs 位置参数）

按顺序问：

1. 这是一个**不同的动作**或**不同的操作对象**吗？→ 子命令。
   - 对象多且动作多：用 noun-verb 两级，如 `app db migrate`、`app user list`。动词从统一动词表选：list / get / create / delete / update / run / show（择一套，别混用）。
   - 父命令只做分组，本身不执行动作（`app db` 单独运行应打印该组帮助）。
   - 层级最多两级（名词+动词）；更深说明该拆子工具或该合并。
2. 这是在**修饰同一动作的行为方式**吗（开关、程度、格式、目标环境）？→ 标志。
   - 检验：如果你发现某个"标志"是必填的，或它改变了其余参数的语法，说明它其实是动作——改成子命令。
3. 这是该动作的**核心操作对象**吗？→ 位置参数，且尽量只有一类（可以是同类多个，如多个文件）。两类以上不同含义的位置参数 → 把次要的改成标志。
4. 都不是（环境相关的部署配置、密钥等）→ 环境变量或配置文件，不进命令行。

## 启发式（默认遵循，有更好理由可偏离，但要说明理由）

- 加法优先：能加标志解决的，不改语义、不加命令。但连续加到一个命令拥有 15+ 标志时，反过来考虑是否该拆子命令。
- 先写用法再写代码：动手前写出 3-5 条真实使用示例，念起来别扭的语法不要实现。示例最终放进 help 文本顶部。
- 输出契约：主输出走 stdout，日志/诊断走 stderr；成功退出码 0，失败非 0 且不同错误类别可区分；面向机器的输出提供 --json。
- help 全覆盖：`app`、`app -h`、`app --help`、`app <sub> --help`都应给出帮助；help 里给示例和文档链接。
- 标志顺序无关；支持 `--flag=value` 和 `--flag value` 两种写法（Python 下 argparse/click/typer 默认满足，不要自造解析器）。

## 自主判断区（以下明确由你自由发挥，不要保守收紧）

- 命令的内部实现结构、代码组织、用哪个解析库（argparse/click/typer 均可，与项目现状一致即可）。
- help 文案、错误消息的措辞与详略。
- 是否提供额外便利（shell 补全、颜色、进度条）——加分项，自行取舍。
- 动词表/名词表的首次制定：从现有命令归纳，选最主流的一套即可，不必征求确认；制定后写入 cli-spec.md 就成为 R2 的约束。

## DONE_WHEN（每次接口变更的验收清单）

- [ ] 重叠分析已输出，且结论是"扩展"或"新增+理由"之一（R1）
- [ ] 新名字通过命名检查：有长名、无近义冲突、术语与词表一致（R2）
- [ ] 若删/改了已发布接口：弃用台账已登记，旧入口是转发别名（R3）
- [ ] cli-spec.md 与代码在同一提交中一致（R4）
- [ ] 全部 help 路径可运行且包含新接口的示例
- [ ] 破坏性命令有确认/--force/--dry-run（R5）

## 一个体现意图的例子

需求："给系统加导出用户数据的功能。"

- ✗ 拍脑袋：新增 `app dump-users --csv`。（已存在 `app user list --json`，功能重叠 70%；dump 与全 CLI 的动词表冲突；--csv 与已有的 --format 概念重复。）
- ✓ 正确路径：读 cli-spec.md → 发现 `app user list` → 结论是扩展：给它加 `--format csv|json` 与 `--output FILE`，并在 spec 术语表确认 format/output 为既有词条。零新命令，需求达成。

反向例子（体现"意图优先于步骤"）：需求是"临时给运维排查加个内部命令，下周删"。此时 R3 的弃用流程不适用——它的意图是保护外部契约，而这个命令根本不进入契约。正确做法是标记为 hidden、在 cli-spec.md 登记为 experimental 并写明删除条件，而不是机械地走 N+2 弃用周期。
