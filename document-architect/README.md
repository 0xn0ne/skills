# document-architect —— 正式工作文档内容架构师

> 以读者为中心，把零散材料设计成一份能读懂、能信服、能照做的正式工作文档。方法论 = **一个核心（以读者为中心）+ 三大支柱（结构清晰·内容精准·表达简洁）+ 六项准则（清晰·简洁·准确·完整·一致·礼貌）**，覆盖报告、方案、SOW、制度、汇报、复盘七类文体。

## 这是什么 / 给谁用

**不是**：给一句话就吐一篇"标题 + 要点 + 表格"的流水文，或套模板填空（章节齐全、每章三行空话）。
**而是**：让 agent 扮演**内容架构师**——动笔前先回答"写给谁 / 为什么写 / 他们需要什么"，再按五步工作流产出，交付前逐条过六项准则（[`./SKILL.md`](./SKILL.md) §6）。

| 适合谁 | 典型场景 |
| --- | --- |
| 项目经理 / 交付负责人 | 给客户写 SOW、服务方案、验收与汇报材料 |
| 职能与管理者 | 年度/季度工作汇报、情况说明、请示与建议书 |
| 咨询 / 研究岗 | 分析、研究、评估、调研报告 |
| 制度与流程 Owner | 制度、规范、流程文件的起草与改写 |

**不适合**：创意写作与文学创作、几十字的短消息、纯代码/配置文件。这些场景加方法论反而是负担。

**触发时机**（见 `SKILL.md` frontmatter 的 `description`）：用户说"写 / 起草 / 整理 / 改写一份报告、方案、汇报、总结、制度、SOW、建议书"，或给一堆背景材料要求成文，或要求"做个分析 / 评估 / 复盘"——即使没说"正式文档"也应触发。

## 核心能力

- 🎯 **读者三问先行** — 读者、目的、必答问题没答案就不动笔，结构由读者的 5-10 个核心问题逆向设计，不套模板。
- 🧱 **三大支柱** — 逻辑（结构清晰）/ 内容（精准务实，含"方法·对象·标准·角色·产物"五个具体）/ 表达（简洁明确，删赘去软化）。
- 📚 **七类文体各有章法** — 每类给出必答问题集、常见主线、专属规则（如制度的 must/should/may 用词分级、调研报告的事实/观点/推断三分法）。
- 🔍 **缺口三选一** — 素材缺口只能走"问用户 / 用领域知识补 / 显式 `[待确认]`"三条路，不允许静默猜测，也不允许编数字。
- ✂️ **换名测试** — 替换客户名/项目名后能原样套用到任何同类项目的段落，判为无效，必须重写或删除。

## 快速开始

### 安装

本 skill 遵循通用的 **Agent Skills 规范**（一个目录 + 一份带 frontmatter 的 `SKILL.md`），不绑定任何特定 agent。把目录放进你所用工具的 skills 目录即可：

```bash
git clone https://github.com/0xn0ne/skills.git
cp -r skills/document-architect/ <你的 agent 的 skills 目录>/
```

常见 agent 的 skills 目录：

| Agent | 用户级（全局可用） | 项目级（团队共享同一版本，推荐） |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/` | `<project>/.claude/skills/` |
| OpenCode | `~/.config/opencode/skills/` | `<project>/.opencode/skills/` |
| 其他支持 Agent Skills 的工具 | 按其文档指定的 skills 目录 | 同上（团队共享同一版本） |

> 不安装也能用：直接在 prompt 里给出 `SKILL.md` 的绝对路径，让 agent 加载即可。

自检（以 Claude Code 用户级为例）：`ls ~/.claude/skills/document-architect/SKILL.md` 应能列出文件。

加载方式：由 agent 依据 `SKILL.md` frontmatter 的 `description` 自动触发；也可在 prompt 中显式给出绝对路径强制加载。

### 最小调用（给 agent 的 prompt 模板）

```text
你是一名内容架构师。

任务：撰写一份 [文体，如：年度工作汇报 / 项目 SOW / 复盘报告]，主题是 [主题]。
读者：[决策层 / 执行团队 / 客户方 / 监管方]
核心目的：[说服决策 / 规范行为 / 汇报进展 / 沉淀经验]
背景材料：[粘贴材料，或给出文件路径]
篇幅与模板：[可选，用户指定时优先遵守]

加载 SKILL（绝对路径）：<你的 skills 目录>/document-architect/SKILL.md
严格按其五步工作流与六项准则执行，只交付文档本体 + 不超过 5 行的交付说明。
```

> 提示：prompt 里只给任务与材料，**不要复述 SKILL 的规则**（规则由 `SKILL.md` 负责）。

### 预期输出

| 产出 | 说明 |
| --- | --- |
| 文档本体 | Markdown（或用户要求格式），按文体常见主线分章，每章有章首定向、主体段落、收束 |
| 交付说明 | ≤ 5 行：采用的关键假设、待用户确认项、被弃用的重要素材及原因 |

成功判据（`SKILL.md` §0）：读者读完能回答「是什么、为什么重要」→「怎么做、为什么这么做」→「我要做什么」；只能说"大概知道有这么个事"即算失败。`SKILL.md` 未强制输出路径，路径由你在 prompt 中指定。

## 支持的七类文体

| 文体 | 侧重 | 一句话必答 |
| --- | --- | --- |
| 分析 / 研究 / 评估报告 | 客观性、分析深度 | 结论是什么？证据何在？对读者意味着什么？下一步做什么？ |
| 调研报告 | 用事实和数据说话 | 调研了谁、怎么调的、发现了什么、说明了什么、建议做什么？ |
| 方案 / 提案 / 规划 | 前瞻性、指导性 | 解决什么问题？怎么做？谁做、何时做？做到什么标准？风险如何应对？ |
| SOW / 工作说明书 | 边界清晰、可验收 | 做什么、不做什么？双方各承担什么？交付什么、怎么验收？ |
| 制度 / 规范 / 流程 | 权威性、约束力、可执行 | 适用于谁？必须/应当/可以做什么？违反后果？谁解释、何时生效？ |
| 工作汇报 / 情况说明 | 针对性、时效性 | 目标达成了吗？什么变了、为什么？需要什么决策或支持？ |
| 总结 / 复盘 | 真实性、可复用 | 原目标是什么？差距在哪？根因是什么？后续改什么、谁负责？ |

每类的**完整必答问题集、常见主线、专属规则**见 [`./references/genre-guide.md`](./references/genre-guide.md)；文体不在表中时（如请示、建议书、白皮书）按"最接近的文体 + 读者三问"推断。

## 工作流（五步）

```
① 明确目的与受众    ② 搭建逻辑框架          ③ 撰写          ④ 修改润色         ⑤ 审核定稿
   读者三问            素材清单（利用率≈100%）  按章节地图写     1 删赘             六项准则逐条过
   核心一句话          缺口清单（三条路）        深度与依据优先   2 句子（R9 主语）  通过后交付
   R8 模糊处理         章节地图 + 术语表        不写空壳章       3 一致 + 4 语气    + ≤5 行交付说明
   ── 内部规划，不输出 ──                                       + 聪明的怀疑者测试
```

前两步是内部规划，不出现在交付物里，跳过则后面的规则救不回来；长文档每写完一个一级章节，回看一次"核心一句话"和章节地图防漂移。

### 九条红线（违反即失败，摘要）

| 编号 | 红线 |
| --- | --- |
| R1 | 不捏造结论、数字、因果关系（用领域知识补方法论缺口是允许的，编数字不是） |
| R2 | 无空壳章节——每章必须有实质正文，不能"仅标题 + 表格/列表" |
| R3 | 不断裂主线——每章说得出与前后章的逻辑关系 |
| R4 | 不空泛——禁止无信息增量的过渡段和套话（制度条文本身除外） |
| R5 | 换名测试通过——换名后通用且无方法/数据/判断的段落必须重写 |
| R6 | 兜底句配额——同一含义免责句全篇一次，收进"假设与前提" |
| R7 | 交付纯净——不含素材盘点、主线笔记、自检过程等元话语 |
| R8 | 关键模糊不静默猜测——能问就问（并附建议方向），不能问就写明确假设 |
| R9 | 责任句有主语——"将开展整改"不合格，"运维组 3 月 15 日前完成整改"合格 |

## 输入 / 输出契约

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 文体 / 任务 | ✓ | 七类之一，或用户指定（按最接近文体推断） |
| 主题与背景材料 | ✓ | 数字、名称、日期、范围、约束、既有结论——尽量给全 |
| 读者 | × | 能从上下文推断则不问（如"给领导汇报"→ 决策者、要结论与选项） |
| 核心目的 | × | 传递信息 / 说服决策 / 规范行为 / 汇报进展 / 沉淀经验 |
| 篇幅与模板 | × | 用户给了模板则以模板优先（含空章处理规则 A9） |

## 反模式

| 反模式 | 为什么坏 | 怎么做 |
| --- | --- | --- |
| 一上来就按模板列章节 | 结构来自模板而非读者问题，必然出现空壳章节（R2/R4） | 先列读者的 5-10 个核心问题，再排序成章 |
| 用表格替代正文 | 表格是辅助，不能承载因果解释和判断 | 过准入测试才用表（[`./references/tables.md`](./references/tables.md)），且表前说明 + 表后解读 |
| 缺数字就编一个"约 30%" | R1 捏造，且会在客户/领导追问时崩 | 走缺口三选一：问用户 / 领域知识补 / 写 `[待确认]` |
| 给不同读者同一版内容 | 决策者要结论与代价，执行者要步骤与窗口 | 按读者裁剪深度、术语、要他做的事 |
| "加强管理""确保有效""尽快完成" | 无主语、无标准、无时限，不可执行 | 写成"谁 + 做什么 + 何时 + 达到什么标准" |
