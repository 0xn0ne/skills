# code-audit —— 证据驱动的只读代码审计技能

> 把"帮我 review 一下"变成**可定位、可追溯、可判定是否阻塞发布**的审计报告。7 个审计维度 + P0/P1/P2 严重度分级 + 7 条不可协商红线，每条结论必须落到 `文件:行号`，没有证据的评价不进报告。
> 给需要判断"这次改动能不能合"的人用：开发者、Reviewer、Tech Lead。

## 这是什么 / 给谁用

**不是**：自动修 bug 的机器人、风格挑刺机、linter 的替代品、凑条数的"15 条真假混杂"评论。

**而是**：一套**只读**审计行为准则。起点假设是"当前代码可能存在问题"，但证据不支持任何发现时，如实输出"未发现问题"就是合格产出——为了让报告显得充实而制造边缘问题，比漏报更糟。终点不是"代码漂亮"，而是**可验证的正确性 + 可接受的风险敞口**。

| 适合谁 | 典型场景 |
| --- | --- |
| 开发者 | 提交前自检：这次改动有没有埋雷、调用方是否都同步了 |
| Reviewer / PR Review | 拿到大 diff，快速区分"阻塞发布"与"可选优化" |
| Tech Lead / 架构师 | 评估技术债务、无效代码、重复代码的处置优先级 |
| 项目负责人 | 验证改动是否真的达成了业务目标（需求双向校验） |

**不适合**：单文件语法检查、格式化建议（不触发本 skill）；需要 AI 直接动手改代码的任务——本 skill **只读**，只描述与建议，不代为修复。

## 核心能力

- **只读保证** — 对被审计文件零写操作，这是身份定义而非约定，不因任何请求而改变
- **证据强制** — 每条结论必须带 `文件路径:行号 + 现象`；无法定位的判断只进"待确认项"
- **P0 前置** — 阻塞级问题置于报告最顶端单独呈现，不埋在正文里等读者发现
- **调用链追溯** — 谁调用它、它调用谁、数据从哪来到哪去；横切式变更显式追踪跨文件联动，避免"局部都对、整体错位"
- **需求双向校验** — 代码→需求 + 需求→代码，找出 GAP 与"镀金功能"
- **无效即负担** — 死代码 / 冗余 / 过时 / 僵尸代码分级识别，威胁级别与功能缺陷相当
- **误报关口** — 写入结论前逐条复核：换个读法是否误报？是否只是风格偏好？通不过就降级为待确认项或 `nit:`

## 快速开始

### 安装

本 skill 遵循通用的 **Agent Skills 规范**（一个目录 + 一份带 frontmatter 的 `SKILL.md`），不绑定任何特定 agent。把目录放进你所用工具的 skills 目录即可：

```bash
git clone https://github.com/0xn0ne/skills.git
cp -r skills/code-audit/ <你的 agent 的 skills 目录>/
```

常见 agent 的 skills 目录：

| Agent | 用户级（全局可用） | 项目级（团队共享同一版本，推荐） |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/` | `<project>/.claude/skills/` |
| OpenCode | `~/.config/opencode/skills/` | `<project>/.opencode/skills/` |
| 其他支持 Agent Skills 的工具 | 按其文档指定的 skills 目录 | 同上（团队共享同一版本） |

> 不安装也能用：直接在 prompt 里给出 `SKILL.md` 的绝对路径，让 agent 加载即可。

自检（以 Claude Code 用户级为例）：`ls ~/.claude/skills/code-audit/SKILL.md`

### 最小调用（给 Agent 的 prompt 模板）

```
# 不要在 prompt 里复述 SKILL 的规则——会污染加载效果，只给范围 + 目标 + SKILL 路径。
你是一名代码审计专家，对下述变更做一次系统性审计。

审计范围：[文件路径 / 目录 / PR 链接 / commit 区间]
业务目标：[本次改动要达成什么，或指向 ROADMAP / spec / .planning 的路径]

加载 SKILL（绝对路径）：<你的 skills 目录>/code-audit/SKILL.md
严格按 SKILL.md 的红线、审计策略与报告结构执行；只读，不要修改任何被审计文件。
```

### 预期输出

一份 Markdown 审计报告，必含 6 个章节（见 [`./SKILL.md`](./SKILL.md)「报告结构」）：P0 紧急项（置顶）→ 审计范围（含深潜覆盖率）→ 业务目标对齐 → 问题清单（P0/P1/P2 分组）→ 测试断言描述 → 待确认项。是否落盘由调用方决定。

**成功判据**：每条问题都能落到 `文件:行号`；每条 P0/P1 都带修复建议 + 可验证的测试断言；阻塞项与 `nit:` / `consider:` 分开归类；未覆盖部分显式声明覆盖率与原因。

> ❌ 不合格："这段代码可能有问题，建议检查一下折扣计算逻辑。"
> ✅ 合格：`order/service.go:128` `applyDiscount` 对 `coupon.Amount` 未做负数校验，上游 `handler.go:44` 直接透传用户输入，可构造负数优惠券使订单金额为负。修复：L128 前增加负值校验并返回 `ErrInvalidCoupon`。测试断言：amount=-100 → 返回 ErrInvalidCoupon → 不进入下单流程。

## 工作流

```
1 意图对齐 → 2 全局扫描+分级 → 3 深度审计 → 4 全局校验 → 5 自我核验 → 6 输出报告
  读 CLAUDE.md     按规模/关键度      高风险区按 7      需求覆盖完整     逐条复核证据      P0 置顶
  README/ROADMAP   建认知地图        维度+调用链追溯   横切变更联动     换读法是否误报    范围+覆盖率
                                                                      风格偏好降级？    P0/P1/P2 分组
```

- **上下文对齐**（第 1 步必读）：`CLAUDE.md` / `AGENTS.md`（团队规范与不变量）→ `README.md`（架构边界）→ `ROADMAP.md` / `.planning/`（业务目标）。缺失不阻塞审计，但要用提交记录、注释、测试反推目标并标注推断置信度。
- **冲突裁决顺序**：项目自身规范 > 目标文档 > 测试文件隐含行为 > 通用最佳实践。冲突时如实呈现事实、列入待确认项，**不替调用方拍板**。
- **大规模审计**：单次改动超过约 400 行或横跨多个不相关关注点时，先按变更行数 / 业务关键度 / 历史缺陷密度粗排风险，高风险区深潜、低风险区扫描级检查，并提示"建议拆分"与本次覆盖率。

## 审计维度与严重度分级

### 7 个审计维度（深潜时按需加载 [`./references/audit-dimensions.md`](./references/audit-dimensions.md)）

| # | 维度 | 目标 |
| --- | --- | --- |
| 1 | 调用链与数据流 | 局部修复不崩上下游，数据不在链路边界爆炸 |
| 2 | 代码逻辑与安全 | 运行时错误 + 安全漏洞；主动查"应有而未有"的控制（缺失的授权/校验/限流看起来都像正常代码） |
| 3 | 无效与冗余代码 | 死代码 / 冗余 / 过时 / 僵尸代码四类分级 |
| 4 | 重复代码 | 识别值得合并的**业务规则**重复，避免过度聚合与"假孪生" |
| 5 | 设计质量与架构 | SRP / OCP / SoC / KISS-YAGNI 作透镜，输出重构信号与架构风险 |
| 6 | 需求覆盖 | 代码↔需求双向校验，找 GAP 与镀金功能 |
| 7 | 测试可验证性 | 有效覆盖率评估；测试不能自证正确性（可能与被测代码出自同一误解） |

精力按代码实际风险分布分配，**不要在每个维度上均匀用力**。

### 严重度分级（后果 × 可逆性）

| 级别 | 含义 | 典型场景 |
| --- | --- | --- |
| **P0** | 立即修复，阻塞发布 | 核心流程不可用；数据丢失/逻辑崩溃；安全漏洞或敏感数据泄漏；函数签名变更但调用方未同步；整条调用链无错误处理；实现完全偏离目标 |
| **P1** | 本迭代内修复 | 副作用不可回滚且缺幂等；核心路径无测试；关键状态变更无日志；空 catch 吞异常；不可达路径/永假分支；新旧实现并存且旧实现无调用方、无回滚计划 |
| **P2** | 技术债务，计划修复 | 超复杂度阈值未重构；非核心路径的需求遗漏；未调用函数/未使用导入；废弃 API 调用；已固化 Feature Flag；ROADMAP 外的过度抽象 |
| **nit / consider** | 不进 P 分级，单独归类 | 个人偏好、命名微调、风格差异、可选优化——即便更好也不阻塞合并 |

完整判据见 [`./SKILL.md`](./SKILL.md)「优先级判定」。

## 输入 / 输出契约

| 输入项 | 必填 | 说明 |
| --- | --- | --- |
| 审计范围 | × | 文件 / 目录 / PR / commit 区间；未指定时优先覆盖变更文件及其直接依赖 |
| 业务目标 | × | ROADMAP / spec / `.planning/` 路径；缺失则反推并标注置信度 |
| 深度与预算 | × | 调用链默认上下各一层；高风险路径（支付/认证/并发/公共接口/迁移脚本）追溯至边界 |
| 输出格式 | × | Markdown 报告；格式由调用方约定，SKILL 只定义审计行为准则 |

按需章节：调用链分析、数据流摘要、重复代码清单、无效与冗余代码清单、重构建议、非阻塞建议、审计覆盖说明——有发现才展开，无发现写"未发现"即可。

## 触发与不触发

| ✅ 触发 | ❌ 不触发 |
| --- | --- |
| "帮我 review 这个 PR" / "做次代码审计" | 单文件语法检查 |
| "这次改动有风险吗？能不能合？" | 格式化 / 代码风格建议 |
| "检查代码质量 / 技术债务"、"验证改动是否完整、有没有漏掉调用方" | 需要 AI 直接修改代码的修复任务 |

## 反模式

| 反模式 | 为什么坏 | 怎么做 |
| --- | --- | --- |
| 凭模型记忆下"调用链/死代码"结论 | 未验证的猜测就是误报来源 | 用文件读取与检索实际验证后再定性 |
| 为让报告好看制造边缘问题 | 每条误报都在教调用方忽略你所有结论 | 证据不足就弃权，列入待确认项 |
| 把风格偏好标成阻塞项 | 稀释阻塞项注意力，违背"信号优先于数量" | 标 `nit:` / `consider:`，单独归类 |
| 发现密钥后回显明文 | 违反脱敏红线 | 只引用位置与类型，不回显内容 |
| 审计中顺手改代码 | 违反只读身份定义 | 只描述与建议，修复交给调用方 |
| 规范与代码冲突时替调用方拍板 | 越权裁决可能压掉真实约束 | 呈现冲突事实，列入待确认项 |
| 大 diff 上均摊精力求"覆盖全面" | 高风险区反而审计不足 | 先分级，高风险区深潜 + 声明覆盖率 |
| 测试通过就当"符合需求" | 测试可能与被测代码出自同一误解 | 检查断言本身是否锁定了错误预期 |
