# 工作类幻灯片创作技能

## 0. 定位：本 Skill 与 ppt-master 的分工

本 Skill 负责"想清楚、查清楚、写清楚"；ppt-master 负责"画出来、导出来"。

| 阶段 | 归属 | 产物 |
| --- | --- | --- |
| 需求澄清、调研核查、大纲、逐页内容、视觉意图、讲稿 | 本 Skill | `project_notes.md`、`outline.md`、`sources.md`、`content.md` |
| 模板/风格选择、SVG 逐页绘制、图表与图片生成、导出 PPTX | ppt-master | `.pptx` 及其工作区 |
| 交付前复核、修订循环 | 本 Skill 发起，ppt-master 执行修改 | 自检报告 |

进入生成阶段时，先读 `skills/ppt-master/SKILL.md` 并完全遵循其路由与门控，本 Skill 不覆盖、不简化它的流程。本 Skill 的产物是它 Plan 阶段的输入。

## 1. 目标与成功标准

### 1.1 为什么做这份 PPT（意图锚点）

一份工作类 PPT 的唯一目的：让**特定受众**在**有限时间**内抓住**一条核心信息**，并做出预期反应（知道、认同、决策、执行、合规）。它是讲述工具，不是文档的排版版。所有步骤未覆盖的情境，用这句话判断：**这样做能否让这群人更快抓住重点并行动？**

### 1.2 DONE_WHEN（每阶段须提交证据，不接受自证"已完成"）

| 阶段 | 完成标准 | 证据 |
| --- | --- | --- |
| 澄清 | 受众、目的、场景、时长/页数、素材、语气、禁区 7 项全部有明确答案或用户确认的默认值 | `project_notes.md` 需求块 |
| 调研 | 每条法规/案例/数据有 ≥2 个独立来源，优先官方；记录名称、条款、生效日期、URL、查证日期 | `sources.md` |
| 大纲 | 每页有：结论式标题、本页目的、要点、建议视觉、时长、与上/下页的承接；用户已确认 | `outline.md` + 用户确认记录 |
| 内容 | 每页 1 个核心观点；正文可在 30 秒内读完；无跳跃、无重复、无立场偏移 | `content.md` |
| 生成 | ppt-master 导出成功；逐页预览已人眼检查（溢出、重叠、对比度、错别字） | 预览截图/渲染结果 |
| 交付 | `.pptx` + 讲稿 + 来源清单 + 自检清单逐项勾选 | 交付包 |

若达标条件与意图冲突（例如字面满足页数但内容被硬拆），停下上报，不取巧。

## 2. 以下必须遵守（红线）

1. **事实可追溯**：法规、案例、数据、引述必须交叉核查，标注来源和查证日期。查不到就写"待确认"并告知用户，不编造、不用记忆填空。
   - 法规优先国内现行有效版本，用全称与准确条款号；核对是否已修订/废止、生效日期是否在演示日期之前。国内无对应规范时才引国外，并注明。
   - 案例优先近 2 年、有官方通报或主流权威媒体报道的；写清时间、行业、手法、后果，不点名个人，企业名以公开报道为准。
2. **敏感信息**：客户/内部数据（事件详情、IP、人名、金额、系统名）默认脱敏或概括化；需要出现原始信息时先问用户。
3. **语气**：正式、客观、中性。描述问题用"现状/风险/建议"，不出现指责性表述，不针对任何部门或个人。面向全员的材料不偏向任何岗位。
4. **一页一观点**：标题即结论。禁止一页多个并列论点、多张图表堆叠。
5. **图表诚实**：坐标轴从零起（或明显标注截断）、单位统一且标注、图表类型匹配数据关系、每张图标来源。
6. **门控**：大纲经用户确认后才进入逐页内容；导出前把关键决策（模板/风格/页数）再确认一次。ppt-master 自身的 ⛔ 门控同样遵守。
7. **不越界扩展**：不添加用户未要求的章节或页数；发现应该补的内容，先提出建议再做。

## 3. 以下由你自主判断（附依据）

- **章节内页数分配**：按内容重要性与受众陌生度分配，而非平均。依据：受众最不熟、最需要行动的部分多给页。
- **叙事结构**：汇报/述职用金字塔（结论先行→论据）；培训用"认知→风险→自身相关→行动"；方案/提案用 SCQA（情境→冲突→问题→答案）或"现状→方案→价值→计划"。可混用，依据是受众决策路径。
- **视觉形式**：优先真实高质量图片/图标；无合适素材时用形状、流程、对比卡片手搓；数据用图表；概念用图示。依据：这页信息是"量"（图表）、"流程"（箭头/步骤）、"对比"（并列卡片）还是"氛围"（图片）。
- **调研深度与并行度**：法规与案例类可并行派出多个子 agent 分渠道调研（官方站、行业协会、安全厂商/咨询机构报告、技术社区、新闻），每个子 agent 只返回结构化摘要（结论、来源 URL、日期、可信度评级），不回传原文。
- **风格取向**：培训偏清晰克制、汇报偏数据驱动、提案偏叙事张力；有品牌模板时以模板为准。
- **是否需要互动点**：培训类每 8-10 分钟安排一个提问/自测/小结页；汇报类不加。
- **何时问用户**：影响结构或立场的模糊点立刻问；纯执行细节自己定并在 notes 里记录理由。一次把问题问齐，不分多轮零碎追问。

## 4. 工作流

### P0 澄清（一轮问齐）

读用户给的全部材料后，用一张表列出 7 项并标注"已知 / 推断（待确认）/ 未知"：受众（层级、背景、痛点）、目的（看完后要知道/做什么，一句话）、场景（现场讲 / 异步阅读 / 两者兼有）、时长与页数（区分内容页与封面/目录/章节/结尾页）、素材（文件夹、数据、模板、品牌规范）、语气与禁区、交付形式。推断项给出默认值，用户不反对即采用。

写入 `project_notes.md`（模板见 §8）。之后每完成一阶段更新一次；上下文过长时只回读此文件恢复目标。

### P1 调研与核查

1. 从大纲需求反推"需要查证的事实清单"（法规、案例、数据、定义、最佳实践）。
2. 并行调研，多渠道：官方（政府/监管/司法）> 行业组织与权威机构报告 > 头部企业与咨询机构 > 技术社区/论坛（用于发现线索，不作为最终依据）。
3. 每条事实交叉核查 ≥2 来源；法规再核一次"现行有效"与条款原文。
4. 写入 `sources.md`：编号、事实陈述、来源 1/2、日期、可信度、用在第几页。
5. 有争议或查不实的，单列"待确认"块交用户。

### P2 大纲（⛔ 用户确认）

按 §8 模板产出 `outline.md`。检查项：

- 每页标题是一句完整判断（有主语有结论），不是话题词。
- 相邻两页的承接能用一句话说出（"上一页讲了 X 的要求，这页看 X 在我们这里的现状"）。
- 章节之间有过渡页或过渡语，防止跳跃。
- 时长分配之和等于总时长；每页 45-90 秒为常态，案例/图解页可到 2 分钟。
- 全员场景检查：随机抽 3 页，问"一个非技术岗员工看这页有关系吗？"

提交大纲并等待确认。用户提出的修改先改大纲再往下走。

### P3 逐页内容与视觉意图

为每页写 `content.md` 条目：标题（结论式）、正文要点（3-5 条，每条 ≤ 20 字，或等效的图示文字）、视觉意图（图表类型 + 数据 + 单位 + 来源 / 图片主题 / 图示结构）、讲稿（口语化、含过渡句与本页时长）、来源编号。

密度自检：一页只有 1-2 个元素、大片空白 → 补视觉或合并；一页超过 6 个元素或正文超过 90 字 → 拆页或砍。

### P4 生成与复核

1. 读 `skills/ppt-master/SKILL.md`，按其路由选择流程（自由设计 / 套用用户模板 / 编辑现有 PPTX），把 `outline.md`、`content.md`、`sources.md` 和素材提供给它；沟通模式、阅读模式等选项按 §3 的判断填。
2. 生成后逐页看预览：文字溢出、元素重叠、对比度不足、错别字、图表单位缺失、页码/章节标记连续性。
3. 用独立视角（新对话或子 agent，只给它 `outline.md` 和预览）做一次 Reviewer 复核：逻辑连贯、密度、语气、事实与来源对得上。
4. 问题回到所属层修：内容问题改 `content.md` 再生成，视觉问题走 ppt-master 的修订路径。修订循环上限 3 轮，仍不达标则带问题清单上报。

### P5 交付

交付包：`.pptx`、讲稿（可在 notes 中或单独文档）、`sources.md`、自检清单（§9）逐项勾选结果、"待确认/已知限制"清单。

## 5. 场景速查

| 场景 | 受众典型关切 | 推荐结构 | 每页节奏 | 特别注意 |
| --- | --- | --- | --- | --- |
| 工作汇报 / 总结 | 结果、差距、下一步、要什么支持 | 金字塔：结论 → 关键成果 → 问题与原因 → 计划 → 需求 | 60-90 秒 | 数据口径一致，同比/环比标清 |
| 述职 | 职责履行、价值、成长、目标 | 职责 → 成果（对应职责）→ 不足与改进 → 下阶段目标 | 60-90 秒 | 用事实和数据替代形容词，不贬低他人 |
| 培训 / 宣讲 | 与我有什么关系、我该做什么 | 认知 → 风险与案例 → 自身相关现状 → 应知应会 → 小结 | 45-75 秒，案例页可长 | 每章有小结，每 8-10 分钟一个互动点，结尾给可带走的清单 |
| 方案 / 提案 | 解决什么问题、要多少、风险、为什么是你 | SCQA 或 现状 → 目标 → 方案 → 价值 → 计划与投入 → 风险 | 60-120 秒 | 对比方案给同口径评估表，投入与收益单位统一 |
| 复盘 | 发生了什么、为什么、以后怎么防 | 时间线 → 影响 → 根因 → 已做/待做措施 → 机制改进 | 60-90 秒 | 只谈事实与机制，不归责个人 |

## 6. 内容与设计启发式

**标题**：陈述结论，不写话题。"三类高频攻击手法均以邮件和即时通讯为入口" 优于 "攻击手法分析"。目录页、章节页可以用话题词。
**正文**：一页 3-5 条要点，每条一行放得下；同页要点语法结构一致（都以动词开头，或都以名词开头）。能用图示表达的关系（流程、层级、对比、因果）不用文字列表。
**留白**：内容区占页面 50-70%。判断方法：眼睛先落到哪？如果没有明显的第一落点，说明要么太空要么太满。
**连贯**：每页讲稿第一句承接上一页，最后一句引出下一页。章节末放一页"本章小结/关键 3 点"，章节首放一页承接语。
**图表选型**：随时间变化 → 折线；类别对比 → 柱形；构成占比 → 堆叠柱或环形（≤5 类）；相关性 → 散点；流程 → 流程图；层级 → 树/金字塔。饼图超过 5 类改用柱形。每张图：标题写结论，轴有单位，右下角写来源。
**案例写法**：时间 + 行业/规模 + 手法 + 后果 + 与本受众的关联点。5 句以内，配 1 个图示或流程。避免细节到可复现攻击的程度。
**法规写法**：全称（首次出现带括号简称）、条款号、生效日期、对个人/单位的核心要求一句话。多部法规用时间轴或对照表，不逐条罗列原文。
**语气**：用"建议""需要""应当"，不用"必须整改""某部门未做到"。描述现状用数据和事实，评价留给受众。
**可读性**：正文字号不小于 18pt（投影场景 ≥ 20pt）；中文字体不超过 2 种；配色 3-5 色，主色 60% / 辅色 30% / 强调色 10%；文字与背景对比度足够（深底浅字或浅底深字，不用中间灰对中间色）。
**异步友好**：只看标题和视觉能明白 80%；讲稿补足剩下的 20%。

## 7. 边界示例

**正例：用户给的页数与内容量冲突**
用户要求 4 章共 30 页，但第 3 章"当前现状"客户能提供的数据只够撑 3 页。正确做法：在大纲阶段明确指出"第 3 章按现有素材约 3-4 页，建议把多出的页数给第 4 章应知应会（每人可执行的动作更多）"，并列出如果坚持第 3 章更多页需要用户补哪些数据。错误做法：把 3 页内容注水成 7 页，或擅自把第 3 章改成别的主题。
（为什么：意图是让受众抓重点并行动，硬凑页数会稀释重点；擅自改结构违反红线 7。）

**反例：为了"够典型"引用一个流传很广但查不到官方通报的案例**
只有自媒体转述、时间和企业名各版本不一致。错误做法：写进正文并标"网络公开报道"。正确做法：不用；如确实需要这一类型的案例，找有监管通报、法院判决或权威媒体首发的替代案例；实在没有就在"待确认"里告知用户，请其提供或接受删除。
（为什么：红线 1。工作场景里一条被质疑的案例会让全份材料失信。）

**正例：受众是全员，但用户提供的素材几乎全是技术运维数据**
不把运维指标直接搬上页面。把技术指标翻译成与每个人相关的表述（"过去半年拦截的钓鱼邮件中，X% 的目标是非技术岗位"），技术细节放讲稿或附录。
（为什么：红线 3 "不偏向岗位" + 意图锚点。）

## 8. 文件模板

**project_notes.md**

```

# 项目：<名称>  更新：<日期>

## 需求（7 项）

受众 / 目的 / 场景 / 时长与页数 / 素材 / 语气与禁区 / 交付形式 —— 每项标 已知|推断|未知

## 已决策

- <日期> <决策> <理由>

## 待确认

- <问题> <影响范围>

## 阶段状态

P0 ☐ P1 ☐ P2 ☐(用户确认: ) P3 ☐ P4 ☐ P5 ☐

```

**outline.md（每页一条）**

```

## 第 N 页 | 章节 X | 类型：内容/章节/过渡/小结

标题（结论式）：
本页目的：受众看完这页应该 <知道/相信/会做> ______
要点（3-5）：
视觉：<图表类型+数据+单位+来源 | 图片主题 | 图示结构>
承接：上一页 ______ → 本页 ______ → 下一页 ______
时长：__ 秒
来源：S1, S4

```

**sources.md**

```

| 编号 | 事实陈述 | 来源1(URL,日期) | 来源2(URL,日期) | 现行有效? | 可信度 | 用于页 |

```

## 9. 交付前自检清单

内容

- [ ] 每页标题是完整判断句（目录/章节页除外）
- [ ] 每页只有一个核心观点；正文 30 秒内可读完
- [ ] 相邻页承接可用一句话说出；章节间有过渡
- [ ] 法规名称/条款/生效日期核对现行有效；案例有 ≥2 来源
- [ ] 数据口径、单位、时间范围全篇一致；每张图有来源
- [ ] 无指责性表述；无偏向特定岗位/部门；敏感信息已脱敏
- [ ] 页数、时长与需求一致（分别核内容页与非内容页）

视觉

- [ ] 无文字溢出、无元素重叠、无被裁切的图
- [ ] 字体 ≤2 种，正文 ≥18pt，配色与模板/品牌一致
- [ ] 图表坐标轴从零或明确标注截断；类型匹配数据关系
- [ ] 页码、章节标识连续

交付

- [ ] .pptx 可正常打开并可编辑
- [ ] 讲稿含每页时长与过渡句
- [ ] sources.md 与页面引用一一对应
- [ ] 待确认/已知限制清单已列出

## 10. 规则来源（维护用）

| 规则 | 对应的观察到的失败 |
| --- | --- |
| 红线 1 法规/案例交叉核查 | 引用已修订法规旧条款、案例细节与官方通报不符，现场被质疑 |
| 红线 3 语气中性 | 培训材料被解读为针对某部门，引发抵触 |
| 红线 4/§6 密度 | 一页仅 2 句话空白过半；或一页 3 张图表受众抓不住重点 |
| 红线 5 图表诚实 | 截断坐标轴放大差异、同页单位不统一 |
| §4 P2 承接字段 | 上一页讲法规下一页突然跳到无关场景 |
| §3 全员视角 | 素材偏技术导致内容偏向 IT 岗位 |
