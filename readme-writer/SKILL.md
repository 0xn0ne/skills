# readme-writer

## 0. 角色与意图（Intent First）

### 你要达成的效果

README 是仓库首页，不是文档全书。读者应在短时间内完成：

1. 判断「这是不是我要的」；
2. 以最低摩擦跑通一次真实成功；
3. 知道下一步学什么、怎么求助、能否贡献、许可证是什么。

### 为什么

- 差 README → 零采用、重复 Issues、贡献者流失。
- 好 README → 降低支持成本、提高信任与 time-to-first-success。
- 过长或过空都会失败：过空无人能用；过长无人愿读。信息应分层，详情外链。

### 工作方式

- 先推断项目类型与主受众，再选章节与深度（见「自主判断区」）。
- 步骤是实现意图的手段；步骤未覆盖时，用本节意图推断，而不是卡住或堆砌模板。
- 同一概念全文用词一致；面向人类可扫读，也便于维护者修改。

## 1. 门槛 / 红线层（不满足则不能交付为「完成」）

> 以下为必须遵守。违反则输出无效，应返工或明确标注阻塞。

### 1.1 意图对齐

- 必须先回答（写在文内或等价体现）：做什么、为谁/为何有用、如何开始、何处求助、许可与贡献态度。
- 禁止用「套全站模板」代替对具体项目的判断；禁止首屏长篇背景/原理而迟迟不出现价值与可运行路径。
- 若项目明确不接受贡献或已停止维护，必须在靠前位置诚实写明（Project status）。

### 1.2 可执行性

- 所有安装/运行命令必须是可复制的完整命令，且与项目真实包名、入口、脚本一致。
- 禁止无法落地的空话：「适当配置」「按需安装」「确保环境正确」——除非紧跟可操作标准（版本、文件、变量名）。
- 若上下文缺少关键事实（包名、许可证、启动命令），必须：
  - 从仓库文件推断（package.json、pyproject.toml、go.mod、LICENSE、Makefile 等）；或
  - 输出中用 `TODO(human): ...` 标出，不得编造版本号、API Key 获取方式、不存在的脚本。

### 1.3 可验证性 / 契约（DONE_WHEN）

交付物在声称「完成」前，应满足：

- [ ] 存在 Title + 清晰一句话描述（做什么 + 对象或场景）
- [ ] 存在可运行的 Quick Start（或文档型仓库的等价「5 分钟理解/使用路径」）
- [ ] Quick Start 含：前提、命令、（如适用）预期输出或成功判据
- [ ] 有 License 陈述（名称/SPDX 或 UNLICENSED + 指向），或显式 TODO
- [ ] 贡献态度明确（欢迎 / 仅接受某类 / 暂不接受 + 链接若有）
- [ ] 无断裂的站内锚点；外链不故意留空占位（未知则 TODO）
- [ ] 未把密钥、令牌、内网地址等敏感信息写入示例（用占位符）

### 1.4 安全边界与可逆性

- **红线**：不得在 README 中写入真实密钥、密码、私钥、生产连接串；示例一律 `your_api_key` / 环境变量占位。
- **红线**：不得伪造合规徽章、下载量、测试通过状态。
- **红线**：不得将 GPL/专有等许可证误标为 MIT 等；不确定则 TODO，不猜测。
- 高影响但可逆：大段删除已有 README 内容前，若用户未要求「全量重写」，应保留信息并迁移/合并，或先给出结构提案。
- 不可逆+高影响（覆盖用户未备份的定制文案、删除法律相关段落）：需在输出中警示，或分步提供 diff 式修改建议。

### 1.5 红线排版（单独成节，便于扫描）

```
RED LINES:
1. 不编造项目事实（命令、许可证、徽章状态、维护状态）
2. 不写入真实密钥/凭证
3. 首屏必须让人理解「是什么」；禁止价值主张被 TOC/徽章/长文淹没
4. Quick Start 必须可验证成功，禁止「只安装不运行」的假上手
5. 不把完整 Reference 级 API/全部配置无节制塞进 README（应链出）
```

## 2. 质量层（决定好不好）

### 2.1 可靠性

- 消除自相矛盾（例如前文说 zero-config，后文要求必填 10 项）。
- 关键决策给依据：章节取舍写在（可选）简短「设计说明」或思考中，最终 README 本身保持干净。
- 输出结构稳定：优先使用下文「推荐骨架」，按项目类型增删，不随机重排核心顺序。

### 2.2 鲁棒性

- 输入残缺时：基于仓库信号降级交付「最小可行 README」+ TODO 列表，而不是拒绝或幻觉补全。
- 多包 monorepo / 多入口：在 Quick Start 标明默认路径，并链到子包 README 或 docs。
- 示例代码风格与项目一致（语言、包管理器、缩进）；未知则选生态最常见方式并注明。

### 2.3 连贯性

- 单一叙述主线：价值 → 证明 → 上手 → 使用 → 深入链接 → 社区与法律。
- 同一功能不要在 Installation / Usage / Quick Start 重复三套互相不一致的命令。

### 2.4 可释性

- 对非常规结构（例如把 Configuration 提到 Usage 前）应能说明原因（用户任务流需要）。
- 关键占位 `TODO(human)` 应说明缺什么信息。

### 2.5 可读性

- Markdown 分级标题清晰，不跳级；列表与表格用于可扫读信息。
- 短句、少行话；必要术语首次出现可轻微解释或链出。
- 代码块标明语言；命令与输出分开。
- 长 README（>~100 行）加 TOC，但 TOC 不占首屏核心位置（可放在描述与 Quick Start 之间或之后）。

### 2.6 抗漂移

- 多轮修改时，维持「已约定的受众、项目一句话、许可证、包名」不变，除非用户更正。
- 子任务（只改 Quick Start）不得无意改写 License/安全段。

## 3. 规模化 / 可持续层

### 3.1 效率经济性

- 默认生成「够用」而非「百科」；扩展章节按需。
- 重复出现的完整 API/changelog/架构 → 链接到现有 docs，不在 README 复制长文。
- 徽章适量（通常 3–6）；不为装饰而堆。

### 3.2 可持续性

- 模块化：骨架固定 + 可选块；用户改需求时只动相关块。
- 示例与脚本名尽量引用仓库真实 source of truth（如 `npm start` 对应 package.json），减少双源腐烂。

### 3.3 可通用性

- 通用原则（首屏、Quick Start 契约、诚实、分层）适用于库/CLI/服务/前端应用/数据科学/内部工具。
- 任务相关规则见「项目类型启发式」，用启发而非硬编码唯一模板。

### 3.4 可组合性

- README 与 CONTRIBUTING.md、CODE_OF_CONDUCT.md、SECURITY.md、docs/ 分工清晰：
  - README：入口与最短路径 + 链接
  - 其他文件：深度流程与政策
- 不在此 Skill 内强制生成全套社区文件；若缺失且项目需要，可建议创建并只在 README 中链接。

## 4. 推荐骨架（默认顺序）

按项目需要省略可选块；**不要为填满而编造**。

```markdown
# {项目名}

{一句话描述：做什么 + 为谁/什么场景}
{可选：一行 tagline}

{可选：徽章行}

{可选：Demo 图/GIF/视频}

## Features          # 或 Why / Highlights：3–5 条，结果导向
## Quick Start       # 必选（文档站可改为 "5 minutes to X"）
## Installation      # 可与 Quick Start 合并（极简项目）或拆分
## Usage             # 主路径示例 + 可选进阶
## Configuration     # 可选：表格式
## {API | Development | Project structure | Troubleshooting | ...}  # 按需
## Contributing
## License
{可选：Acknowledgments / Support / Security / Roadmap / Maintainers}
```

**Standard Readme / Make a README / Open Source Guides 对齐点**：Title、描述、Install/Usage、Contributing、License 为默认核心；其余按信号添加。

## 5. Quick Start 专项规范

### 意图

最大化 time-to-first-success，建立「这东西能用」的信任。

### 必须包含

1. **成功定义**：完成后用户看到什么  
2. **前提**：运行时版本、账号、工具（写在命令前）  
3. **最短命令序列**（宜 ≤5 步）  
4. **预期输出或成功判据**  
5. **下一步链接**（Usage / 完整安装 / 概念文档）

### 写法启发

- 只保留默认最常见路径；Homebrew/yarn/conda 等放 Installation 或折叠。  
- 需要密钥时：写明获取处 + 环境变量名，不写真实值。  
- 复杂项目：Quick Start 用 Docker one-liner 或官方脚手架，完整开发环境放 Development。  
- 参考 GitHub Quickstart：点明受众、前提、将完成的事项；步骤可略简；重 code block；结尾 Next steps。

### DONE_WHEN（Quick Start 段）

- 陌生开发者仅凭该段 + 公开前提，能在干净环境达到所述成功判据（或文档型：完成所述「理解/操作」目标）。

## 6. 必须遵守 vs 自主判断

### 必须遵守

- 红线层全部条款  
- DONE_WHEN 检查清单  
- 不编造事实；敏感信息占位  
- 核心问题（what / why / how to start / help / license-contrib）有着落  
- Quick Start 可验证  
- 中文或英文与用户/项目主导语言一致（用户指定优先）

### 以下由你自主判断

- 是否需要 TOC、Features 用表还是列表、Demo 用 GIF 还是静态图  
- Installation 与 Quick Start 合并还是拆分  
- 是否增加 Architecture / Roadmap / Built With / 多语言 README  
- 徽章集合与是否居中等排版美学  
- 章节标题用词（Getting Started vs Quick Start）——保持生态习惯即可  
- 内部工具 vs 公开 OSS 的语气（仍须清晰，但 CoC/贡献篇幅可不同）  
- 当用户只要「补写 Usage」时，不主动重写全文（除非明显损坏一致性）  
- 项目类型启发式的具体应用强度（见下）

### 未标注的模糊地带

- **默认**：选择更有利于 time-to-first-success 与诚实清晰的方案，并在必要时用一句话说明取舍。  
- **不要**默认保守到只输出 Title+License 空壳；也**不要**默认生成 200 行万能百科。  
- 信息不足时：最小可行 + 显式 TODO，优于沉默或幻觉。

## 7. 项目类型启发式（非穷尽）

| 类型 | 加重 | 可减弱 |
| ------ | ------ | -------- |
| 开源库/SDK | Install、Usage 代码、API 链接 | 长 Deployment |
| CLI 工具 | 安装后一条命令 + 帮助输出 | 重 GUI 截图 |
| Web/App | Demo 图、本地/部署 Quick Start | 过深 API |
| 服务端/Infra | Docker Compose/K8s 最短路径、配置、安全联系 | 炫酷徽章墙 |
| 数据/科研代码 | 数据前提、复现实验步骤、引用 | 强 Contributing 社区文案 |
| 文档/规范仓库 | 「如何阅读/采用」路径；Install 可省略 | 强 Usage 代码 |
| 内部企业仓库 | 与公司平台链接、oncall、目录结构 | 营销式 Features |

## 8. 工作流（意图下的推荐步骤，非唯一剧本）

1. **校准**：受众、语言、新建还是改写、项目类型、已有 docs 与 LICENSE。  
2. **收集事实**：从仓库读取名称、描述、脚本、许可证、示例；列出未知项。  
3. **定骨架**：核心层必选 + 扩展层按需。  
4. **写首屏**：名称、一句话、（可选）视觉与 3–5 条价值。  
5. **写 Quick Start**：前提 → 命令 → 输出 → 下一步；并自检可运行性。  
6. **补 Installation/Usage/其他**：与 Quick Start 不打架。  
7. **页脚**：Contributing、License、Support/Security 等。  
8. **自检 DONE_WHEN + 红线**；输出 README +（若有）TODO(human) 与简短取舍说明。

边界 case（步骤未覆盖）：回到「0. 角色与意图」——优先保证可理解、可上手、诚实、可维护，而不是卡在缺某一可选节。

## 9. 正反例（体现意图，非套步骤）

### 正例（意图：先成功再深入）

- 一句话后直接 GIF，再 Quick Start 三行命令 + 输出，Installation 链到多 OS。  
- Monorepo 写明 `cd packages/cli && ...`，根 README 不假装只有一个包。

### 反例（违背意图）

- 先 800 字架构哲学，无命令。  
- `pip install .` 后无任何 run/示例。  
- 徽章显示 build passing，与仓库坏掉的 CI 不一致（编造可信度）。  
- License 写 MIT，仓库无 LICENSE 或实为专有（法律错误）。

## 10. 输出格式约定

- 主产物：`README.md` 内容（Markdown）。  
- 若有信息缺口：文末或单独块 `## TODO for maintainers`（也可在对话中列出）。  
- 若用户要「指南/规范」而非具体 README：输出本 Skill 的人类可读摘要版，不与具体项目 README 混淆。  
- 引用外部最佳实践时不必在 README 内堆链接；需要时在对话层说明来源即可。
